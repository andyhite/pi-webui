# PlotRoom — Enforcement

**Scope.** For each rule the spec states, the single predicate that decides it, the refusal vocabulary it speaks, and which surfaces call it — the map from a governing principle to the one place in code that makes it true. Details spec §2, §3.4, §3.7, §3.8, §6.6, and §8. Record shapes live in [data-model](data-model.md); how sessions and runs move through these gates lives in [session-lifecycle](session-lifecycle.md) and [run-lifecycle](run-lifecycle.md); transport mechanics live in [interface-contract](interface-contract.md). Where enforcement has a known gap, the gap is named with its tracker issue rather than smoothed over.

## 1. Actor identity

Every write names its actor — the operator or a specific session — and the product authenticates that identity rather than believing a label (principle 8).

**The predicate:** `parseActor` (`apps/server/src/http/actor.ts`), mounted as `actorMiddleware()` on `/api/*`. It reads the `X-PlotRoom-Actor` header: omitted or the literal `human` resolves to the operator; `session:<sessionId>` resolves to that session; anything else — an unparseable actor — is a 400. There is deliberately no representation for an unattributed write.

**The refusal:** not an enum of reasons but a single `badRequest` with the message `actor must be "human" or "session:<sessionId>", got <raw>`. There is exactly one way this gate refuses.

**Surfaces:** every `/api/*` route reads `c.get("actor")` set by this middleware; the WS layer reuses the same `parseActor` function so a socket-originated write is authenticated identically (principle 8's "one rule, identical refusals").

**The honesty note.** The header is **self-declared** by whoever sends the request — a hand-written `curl` or a compromised session can claim to be the operator, and nothing here checks a credential against it (issue #291, open). The bridge (§2 below) is what keeps a _session's own_ tool calls honest, but several routes are not behind that bridge and are ungated against a spoofed actor today (issues #204, #273, #274, #289 — the last is `/api/activity` specifically, missing the operator-only actor gate its neighbors on the attention surface have). This document names the gap rather than the fix: the header format is the contract; who may set it to what is not yet fully closed.

## 2. Reflexivity and lineage

No agent authors intent into its own initiation chain — it cannot wire its own inputs, grant itself capabilities, raise its own budget, or route around any of this through a chain it started (principle 1).

**The predicate:** `checkAuthoring` (`packages/core/src/lineage.ts`). Humans are unconstrained; for a session author it walks `ancestorsOf` in both directions from the author and the target and refuses if either is in the other's chain. A delegation's result returning to the delegator never reaches this check — provenance edges don't pass through it — because the delegator already authored that intent when it delegated.

**The refusal:** `ReflexivityRefusal` carries exactly one reason, `own_chain`, with the message "a session cannot author context into itself, its ancestors, or its descendants."

**Tool-call reflexivity** is a layer on top, in `packages/core/src/sessions/tools/reflexivity.ts`: `checkToolCall` resolves a call's `ToolTarget` to the sessions it would reach (via an injected `ToolTargetIndex` — the graph answers what a node feeds, this module states the rule) and refuses with one of `TOOL_CALL_REFUSAL_REASONS`: `unknown_tool`, `own_chain` (principle 1's asymmetry), `human_only` (the operator's own gesture), or `proposal_required` (the target inherently includes the author — propose it and let a human accept, §7 below). The doc-comment is explicit about the two easiest resolutions to get backwards: `run_one` must never resolve to the session it is about to create (that one is a legitimate descendant), and the claim-answer tools must resolve to the **empty set**, never the waiting session — a claim can only be granted from capability the granter already holds, so a grant is never self-authorization.

**The tool bridge** (`packages/core/src/sessions/tools/bridge.ts`) is the structural fix for the header's honesty gap as it applies to a session's own tool calls: a bridge is constructed bound to one session, writes `X-PlotRoom-Actor: session:<id>` on every request from that binding rather than trusting anything the agent supplied, and refuses outright (`actor_supplied_by_session`, one of `TOOL_REQUEST_REFUSAL_REASONS` alongside `unknown_tool`, `missing_input`, `unknown_input`) if the call's input carries any of `RESERVED_INPUT_KEYS` (`actor`, `author`, `headers`, `credential`, and their casing variants) — refused rather than silently stripped, so a session that tries learns the call failed rather than that it quietly succeeded as someone else. Every call goes reflexivity check → request build → transport, in that order, so a refused call never reaches the transport and therefore has no side effect.

**Surfaces:** `sessionLineageGuard` (`apps/server/src/approvals/lineage.ts`) mounts `checkToolCall` in front of `session_stop`, `session_end`, and `session_delete` — the three single-session verbs the run-gesture and injection checks didn't reach on their own (issue #75) — and is ordered **before** `destructionGuard` (§4) so the question "is this even a thing a session may be granted" is settled before "may this session do it," closing the hole where a target-less pre-grant could otherwise cover an own-chain delete.

## 3. Claims

Isolation within a workstream is one writer per path, always, enforced by the model rather than by discipline (principle 4, spec §3.4).

**The predicate:** `createClaimManager` (`packages/core/src/claims/manager.ts`) — pure and deterministic, state in, decisions and effects out, so the canvas, the API, and an agent's `claim_request` tool reach identical verdicts from identical rows. Supporting predicates: `checkGrantExtent` (a grant may not exceed what its granter holds — the capability invariant, principle 1's "a claim redistributes write access, it never creates any"), `authorityFor` (the deepest claim covering a path), and `evaluatePolicies` (`packages/core/src/claims/policy.ts`, deny-first — deny wins at any depth over a more specific allow).

**Canonical paths and hierarchical conflict:** paths are canonicalized once (`canonicalizePath`) before comparison; `pathsConflict`/`isWithin` make `src/` and `src/auth.ts` conflict, and a directory claim covers everything created under it, including paths that don't exist yet.

**Lease bounds:** `DEFAULT_CLAIM_LEASE_SECONDS = 15 * 60`, `MAX_CLAIM_LEASE_SECONDS = 24 * 60 * 60`, `MIN_CLAIM_LEASE_SECONDS = 1` (`manager.ts`). Every requested lease is clamped through `clampLease` into `[MIN, MAX]`, with an absent or non-finite request taking the default rather than being read as "forever" — the clamp is reported back on the granted claim rather than silently applied, so a caller that asked for more reads the real number. Only the operator's root claim is immortal; every other claim is a lease, never a lock.

**The refusal vocabulary:** `CLAIM_REFUSAL_REASONS` (`packages/core/src/claims/model.ts`) — `invalid_path`, `no_such_claim`, `no_such_wait`, `not_holder`, `exceeds_grant`, `policy_denied`, `would_deadlock`, `human_only`, `already_held`, `root_claim_immutable`. Every `ClaimRefusal` carries an actionable message, per §3.4's "it names what the caller holds and what to do next."

**Deadlock:** `packages/core/src/claims/deadlock.ts`. The wait-for graph is over _sessions_, never paths, and the operator is never a node in it (they never wait, so no cycle runs through them). `findWaitCycle(edges, candidate)` checks whether adding a candidate edge to the standing graph closes a cycle — the insertion-time check that refuses the newest claim outright, before the state ever contains the cycle; `findAnyWaitCycle(edges)` finds a standing cycle with no candidate to hang the search on, for the churn case where a promotion hands a path to one waiter and a different waiter's blocker set moves onto it. The message, `describeDeadlock`, is built as `` `granting this would deadlock: ${loop}. ${yours}.` `` where `yours` names what the requester already holds (`"you hold ${holds.join(", ")} — yield one of those to break the cycle"`) or, if it holds nothing, says so plainly — actionable per §3.4.

**Divergence:** `packages/core/src/claims/divergence.ts`. `deriveClaimStaleReads` compares a session's recorded `PathRead`s against later `PathWrite`s and classifies staleness as one of `CLAIM_STALE_CLASSES`: `peer-write` (another session, holding the path, wrote it after this session read it) or `hand-edit` (the operator wrote it by hand — its own class, because co-working with an agent in one workspace is the normal case, not an anomaly). `checkClaimContinuation` layers this onto the workspace-level `checkContinuation`/`forcesFresh` gate: a change is only "blocking" if it both forces-fresh at the workspace level _and_ is not path-attributable to the write ledger (`isPathAttributable`); continuation is refused only when blocking changes or stale reads are non-empty, and describes why via `describeStaleness` — this is what lets continuation be blocked far less often than the conservative workspace-level check alone, and always for a reason the product can name. **The operator is an implicit claim holder:** a `PathWrite`'s `holder` is an `Author`, and a hand edit's `claimId` is null — the write ledger treats the operator's own edits as a first-class holder rather than an anomaly, so a hand edit stales a session only when it touches a path that session actually read.

**The recorded non-path limit (spec §3.4).** The claim vocabulary is paths; principle 4's enforcement today covers the filesystem. A session's work can hold resources that are not paths — a supervised process, a bound port, a browser tab, a live evaluation kernel — and no claim bounds them. The spec's recorded position: anything whose reach crosses the workspace boundary is refused outright, a session-scoped non-path resource is admitted unclaimed but observed, and whether the claim vocabulary itself should extend to a named non-path extent — which would need a machine scope beside workspace and path — is an **open decision** (issue #178).

**Surfaces:** `ClaimService` (`apps/server/src/claims/`) sweeps lapsed leases before every decision and publishes `claim`/`claim_wait`/`claim_policy` on the event stream; `decideToolPermission` (§8 below) calls `manager.checkWrite` for every runtime write before it runs — a driver with no gate wired denies by construction.

## 4. Approvals and pre-grants

A session requesting a capability it does not have raises an approval; irreversibility pierces whatever was pre-granted (spec §6.6, principle 10).

**Ask points:** `ASK_POINTS` (`packages/core/src/commands.ts`) — `external_write`, `irreversible_write`, `destructive_state`, `claim_outside_policy`, `command_dispatch`. `ALWAYS_ASK = ["irreversible_write"]`, and `effectiveAskPoints` computes the union of a definition's declared points with this always-ask set rather than letting a definition opt out of it — the piercing rule is a computed property, not a branch a definition's author could accidentally skip.

**Approval kinds:** `APPROVAL_KINDS` (`packages/core/src/sessions/approvals/ask.ts`) — `tool-permission`, `claim`, `destruction`, `integration-write`, `standing-instruction`. The last is the one kind nothing can pre-grant: `preGrantable` (`pre-grants.ts`) is the sole constructor of a coverage-checkable ask and returns `null` for `isProposalAsk` as well as for `isIrreversibleAsk` — an "allow always" over proposals would apply them silently, which principle 1 forbids a proposal from ever being.

**Irreversibility piercing pre-grants, as a type rather than a branch.** `WriteReversibility` is `"reversible" | "irreversible" | "unknown"` (`packages/core/src/sessions/outside-world.ts`); `isIrreversibleWrite` collapses `"unknown"` into irreversible (principle 7 — an undo nobody can promise is not an undo), so a plugin author's doubt is never silently read as safe. `preGrantable(ask)` returns `null` for any irreversible ask, so there is no `PreGrantableAsk` value an irreversible call could be checked against — `pre-grants.test.ts` pins this with a `@ts-expect-error` rather than a runtime assertion, keeping the rule structural. `preGrantPiercedBy` names, on the raised `Approval`'s `piercedPreGrant` field, the specific pre-grant that _would_ have covered the call had it been reversible — so an operator who configured broad coverage sees which rule was pierced rather than reading the raise as a misconfiguration.

**Destruction atomicity.** `decideDestruction`/`decideDestructionByName` (`packages/core/src/sessions/approvals/destruction.ts`) is the routing decision: `not-destruction`, `allowed` (execute the soft delete), `must-ask` (raise the approval, leave the gesture unexecuted), or `denied`. `checkDeletion` (`packages/core/src/sessions/deletion.ts`) is the store's last line, not the router — every destructive call site gates through it directly (`session_deletion_needs_approval` is its one refusal reason), so a call site that forgot to route through the approval channel fails closed rather than deleting. On the server, `performDestruction` (`apps/server/src/approvals/destruction.ts`) makes the cascade one transaction: a destruction soft-deletes its subject **and** removes the board node in the same unit, because before that was one transaction a failure between the two left a live node whose subject the reads already filter out — a card with nothing behind it — and an approval's recorded effect failure that said the destruction didn't happen about one that half did (issue #76, closed by this atomicity; the direction was open at the time of `destruction.test.ts`'s "cascade is one unit" suite). `destroySession` stops the live session **before** the transaction, deliberately outside it, because a runtime stop is not a row no rollback can un-stop. The corresponding attention-surface gap — a deleted session's queue rows needing their own cleanup — is issue #77.

**Surfaces:** `apps/server/src/approvals/` — `service.ts` (`ApprovalService`, raise/answer/`decideProposal`), `guard.ts` (`destructionGuard`, catalog-driven by each tool's `requires.destroys` rather than a second list, mounted after `sessionLineageGuard`), `lineage.ts` (the reflexivity guard, §2). Ask points route through `packages/core/src/commands.ts`'s declared `ToolPermissions`/`AskPoint`s at the command-definition level and through `packages/core/src/sessions/tools/gate.ts`'s per-call `toolCallAsk` at runtime (§8).

**Open destruction-direction decisions:** issues #292, #77, #194 — none appear in the current checkout's code comments; they are recorded here as open per the assignment brief and should be resolved against the tracker, not inferred from source that doesn't mention them.

## 5. Budgets

Spend is budgeted, not gated, and a session may never exceed the tightest cap that binds it (principle 2, spec §8).

**The predicate:** `resolveEffectiveBudget` (`packages/core/src/budgets.ts`) — the one function the pre-run refusal, the session-facing read, and mid-session enforcement all call, so they cannot disagree (principle 8). Given a list of `BudgetBinding`s it returns `unbounded` if the list is empty, otherwise the binding with the least `remainingMicros` (`remainingOf`, never negative — past a cap the answer is "nothing left," never a debt), and a `BudgetState` of `ok`, `near-cap` (past `warnFraction`), or `at-cap`.

**Transitive binding.** A session is bound by every scope above it — its own run/batch cap, its workstream's, the global ceiling — **and** by the same scopes of every ancestor in its initiation chain, because its spend counts against every budget that binds the initiating work. `BudgetBinding.chargedSessionId` carries this: a binding may belong to an ancestor's run, in which case what it counts is that ancestor's _attributed_ total, which already includes everything its chain delegated — so a child that couldn't see that binding could spend its parent's cap without ever exceeding its own.

**Tightest-cap.** Stated once, above, and never restated as a sum: the rule is the _minimum_ remaining across every binding, not the nearest and never the total.

**`DEFAULT_GLOBAL_CEILING_MICROS = 25_000_000`** — $25/day, the shipped default an operator can raise or remove. **`DEFAULT_BUDGET_WARN_FRACTION = 0.9`** — near-cap starts at nine-tenths spent. `BUDGET_GUIDANCE` is delivered with the warning itself, not left as documentation nobody reads: "Wrap up cleanly: finish or safely stop what you are doing, leave the workspace coherent, and report what is done and what is not. Do not race the budget — skipping verification to fit under it is a failure mode, not a saving." `BUDGET_STATES` — `unbounded`, `ok`, `near-cap`, `at-cap` — carries no refusal-reason enum of its own: reaching a cap is a distinct **outcome** (§3.6's out-of-budget end state), never an error thrown from this module.

**Surfaces:** `apps/server/src/budgets/service.ts`'s `BudgetService` gathers the facts — walking `attributionChain` to find every ancestor's run/batch/workstream scopes plus the global row — and calls `resolveEffectiveBudget`; it deliberately does not stop a session or deliver feedback itself, because a second place that could end a session would be a second way an end state gets recorded (§3.6's taxonomy). **A known actor gap:** `apps/server/src/routes/budgets.ts`'s write routes (`set`, `delete`) call the store directly with no `actor`/`actorOf`/`operatorOnly` reference in the route itself, despite the route's own doc-comment claiming the writes are operator-only — the claim is not yet enforced by the actor the way the attention-triage and claim-manager writes are.

**Capacity as a distinct vocabulary (spec §8).** The concurrency limit — "a configurable global limit bounds how many sessions run at once" (§4.1) — is deliberately **not** a budget: it is admission of already-initiated work, never a spend decision, and queuing beyond it is "deciding _when_, never _whether_" (`apps/server/src/runs/queue.ts`). Conflating the two vocabularies would let a capacity refusal read as a budget refusal or vice versa, which is exactly the kind of drift principle 8 rules out by declaring one vocabulary per concept. The concurrency limit's own configuration surface and its interaction with per-workstream capacity are recorded as open (issues #135, #149); neither issue number nor a capacity-specific refusal enum appears in the current checkout, so this section states the intended separation rather than a shipped enforcement point for it.

## 6. Graph legality and acyclicity

The legal connections are exhaustive — content → command, content → running session, nothing else — and no cycles in command topology (spec §3.7).

**The predicates:** `checkConnection` and `wouldCycle` (`packages/core/src/edges.ts`). `checkConnection(from, to)` is the mid-drag refusal: it returns `{ legal: true }` or a `ConnectionRefusal` with one of `self`, `illegal_target`, `session_not_running`, `source_not_content`, `would_cycle`, `duplicate` — with messages including "a node cannot be its own context" (`self`), "only content can be wired as context" (`source_not_content`), "that session has ended; fork or re-run it instead" (`session_not_running`), and "content cannot be wired into content" (`illegal_target`). `wouldCycle(commandInputs, producerCommand, consumerCommand)` refuses immediately if the two commands are the same node, otherwise does a reachability search over `commandInputs` from the producer and returns true if the consumer is reachable — a command's output may never be, transitively, its own input. This rule is explicitly about command topology only: session-to-session injection is legitimately bidirectional, governed by the lineage rule and budgets rather than by acyclicity.

**Surfaces:** `packages/db/src/graph-store.ts` calls both before writing an edge; `apps/web/e2e/canvas-mid-drag-refusal.spec.ts` and `packages/ui/src/legality/create-menu.ts` verify the same predicate governs the canvas's own drag-time refusal, so an illegal connection never looks legal for even one frame (principle 8, one rule).

## 7. Standing instructions

Only a note or a document at world scope can stand; only a human declares one; an already-standing or already-proposed object is never proposed twice (spec §3.8, principle 1).

**The predicate:** `checkStandingInstruction` (`packages/core/src/sessions/standing-instructions.ts`), backing `markStandingInstruction`. It refuses with one of `STANDING_INSTRUCTION_REFUSAL_REASONS`: `not_world_scope` (a local object belongs to the workstream that produced it — marking it standing would make it readable by workstreams it doesn't belong to), `kind_cannot_be_standing` (only `STANDING_INSTRUCTION_KINDS` — `note` and `document` — qualify; a kind whose content is somebody else's to change, like a ticket or a transcript, would let an external re-sync rewrite the rules every workstream runs under with nobody deciding it), `human_only` (principle 1 — a session marking its own content standing would be authoring into a scope that reaches its own chain), `already_standing`, and `already_proposed` (one object, one open ask at a time — a session may re-run the discovery read as often as it likes, but a fresh proposal on every rediscovery would flood the queue with the same pending question).

**Propose-dedup and no pre-grant coverage.** A session cannot declare a standing instruction directly — it calls `proposeStandingInstruction`, which builds a `ToolProposal` via the reflexivity layer's `proposeToolCall` (§2) rather than performing the act; a human accepts it through `acceptedStandingInstruction`, whose own refusals (`PROPOSAL_APPLICATION_REFUSAL_REASONS`: `not_accepted`, `wrong_tool`, `no_object`) keep "apply" reachable only from an already-accepted proposal. The `standing-instruction` approval kind (§4) is structurally the one kind `preGrantable` can never produce a coverage verdict for — no pre-grant can cover the acceptance, so "allow always" is not an escape hatch here the way it is for a reversible integration write.

**Surfaces:** the tool catalog's `standing_instruction_declare`/`_retire` endpoints are `humanOnly` in `requires`; `resolveStandingInstructions` is called from `RunStore.plan`, so a run's recorded assembled content already contains the standing instructions that applied to it — availability is resolved at assembly time, never fanned out as edges the graph would have to keep in sync.

## 8. The gesture gate

Every gesture a human has is available to an agent as a tool over the same vocabulary; one gate decides every call; a refused call has no side effect (principle 8).

**The predicate:** `decideToolPermission` (`packages/core/src/sessions/tools/gate.ts`). It decides along two independent axes: `WriteIntent` — `none` (touches nothing in the workspace), `paths` (writes exactly the declared paths), or `unbounded` (could write anything — a shell, an unrecognized tool; fail-safe by construction, since an unknown extent always raises an approval rather than being trusted) — which is claims territory (§3.4); and a declared `ToolWorldDeclaration`'s reversibility, which is approvals territory (§6.6, §9.2). The gate is explicit that a tool mis-declared `none` executes ungated — the declaration _is_ the trust boundary, checked by review (`OMP_KNOWN_WRITE_EXTENTS`) rather than validated at runtime, and an unrecognized tool defaults to `unbounded` rather than being trusted by omission.

**Catalog↔route pinning.** `catalog.test.ts` reads the server's actual mounted routes from `apps/server/src/routes` and checks the tool catalog against them in both directions: a `live` tool naming an endpoint that doesn't exist fails, and a mutating endpoint with no matching tool fails unless it's declared operator-only — closing the gap a scanner limited to the catalog's own known HTTP verbs would miss (the test's own history names `PUT /api/settings/:key` as exactly that kind of miss before the scanner widened). This is what keeps "one catalog drives both surfaces" true as code rather than as a claim in a comment.

**The not-yet-delivered in-session registration.** A tool's `availability` field is `"live"` or `"pending"` — `catalog.test.ts` also fails a `pending` tool whose endpoint has since appeared, so the flag can't rot into a lie once the server side lands. `graph_warnings_read` is `pending` today: the tool is fully declared — schema, endpoint, requirements — but not yet exposed to a running session as a callable tool (issue #160, open). Declaring it ahead of delivery is deliberate: the catalog is the one place the vocabulary is stated, and a tool waits here rather than being invented ad hoc the day its endpoint ships.

**Surfaces:** `apps/session-host/src/permission-gate.ts` calls `decideToolPermission` from the runtime's own `tool_call` extension handler, blocking until PlotRoom answers, before any tool executes; `apps/server/src/claims/service.ts`, `apps/server/src/integrations/service.ts`, and `apps/server/src/sessions/driver.ts` are the other call sites, all reaching the same function rather than re-deriving the decision.
